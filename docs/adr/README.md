# Architecture decision log

This is the single record of Richmod's architecture decisions. Each entry keeps the decision, the constraint or reason behind it and the consequence; the long write-ups it replaces are in git history (for example `git show c7dfcec6:docs/adr/ADR-046-universal-review-interaction-projection.md`). `AGENTS.md` requires an entry here for a material architecture change or new infrastructure.

- **Adding one:** append an entry numbered **ADR-060**, in the heading form `## ADR-060: Title` followed by an italic line `*Status · YYYY-MM-DD*` and one short paragraph (decision, key reason, consequence). Where an entry changes an earlier one, update the earlier entry's status line to name it.
- **Current versus superseded:** the status line is authoritative. Superseded or rejected decisions are kept as a short note pointing at the entry that replaced them, so references such as `ADR-037` in code, tests and docs still resolve here.
- **Dates:** the date is when the ADR was first committed unless its own status stated a date; amendments carry their own dates in the entry.
- **Duplicate number:** ADR-033 was used by two decisions on different topics. Both are current and both stay under the number: *Bounded natural conversational finance agent* (what code comments and the Telegram migrations mean by "ADR-033") and *Cloudflare email ingress and two-deploy Gmail sunset*.
- **Contracts that code relies on** (callback grammar, limits, action vocabularies, cache classes) are kept in the entries below; the per-kind review tables live in code (`apps/reviewdomain/reviewdec/kinds.go`) and the schema in `docs/DATABASE_SCHEMA.md`.

## ADR-001: Go backend
*Accepted · 2026-08-25*

Backend services use Go with the standard library, `pgx/v5` and explicit domain code. Financial state transitions stay in Go and PostgreSQL is the canonical store.

## ADR-002: JavaScript Next.js frontend
*Accepted · 2026-08-25*

The web app is Next.js and React with JavaScript, in its own container, and never owns financial-state mutations. ADR-056 later moved serving of the static build into the Go API; the stack itself is unchanged.

## ADR-003: PostgreSQL-backed job queue
*Accepted · 2026-08-25*

Background jobs live in PostgreSQL and are claimed with row locks (`FOR UPDATE SKIP LOCKED`). No separate queue service is introduced.

## ADR-004: Evidence-first canonical ledger
*Accepted · 2026-08-25*

External and manual inputs are kept as evidence. Deduplication links evidence to a transaction; it never deletes evidence and canonical transactions are never hard-deleted.

## ADR-005: Cloud AI Gateway boundary
*Accepted, amended by ADR-030 and ADR-038 · 2026-08-25*

All model inference goes through the Cloud AI Gateway (LiteRouter): `/v1/responses` or `/v1/chat/completions` for generative work, and the distinct `/v1/systemone` protocol for bounded decisions (Jev). System One is never emulated as an OpenAI-compatible chat model, and a failed System One call must not silently fall back to a generative model for the same question. Model output is untrusted: Go strictly decodes generative output and, for System One, checks question keys, answer types, probability ranges, policy thresholds and current server state before it can affect a transition. Richmod authenticates only to LiteRouter and never stores upstream provider credentials (e.g. the TypeSafe key). Logical model policy names come from configuration, not business rules. Deterministic ledger, authorization, binding, arithmetic, reconciliation, review and read flows keep working when the gateway is down; model-dependent work fails closed, asks, retries or defers to Review Inbox.

## ADR-006: Bank Jago SPENDING_ONLY policy
*Accepted · 2026-08-25*

Jago outgoing merchant, QR and debit-card payments may be expense candidates. An outgoing transfer is `UNCLASSIFIED` and excluded from analytics until a deterministic known-account match or explicit review resolves it to EXPENSE, TRANSFER or IGNORE; money leaving Jago alone never makes it an expense. Household-scoped `known_account` rows hold a masked stable `match_hint` (not a full number): `OWN_ACCOUNT` and `HOUSEHOLD_ACCOUNT` resolve to confirmed TRANSFER, `INVESTMENT_ACCOUNT` to a retained voided non-spending reference, and unknown or `OTHER` destinations stay in `TRANSFER_CLASSIFICATION` review. Incoming funding, pocket and RDN movements never become household income or spending.

## ADR-007: Deterministic Jago parser with LLM fallback
*Superseded by ADR-025 · 2026-08-25*

Superseded: Jago email handling is now the generic config-driven pipeline of ADR-025, with no bank-specific parser. The Gmail/Pub/Sub intake details it recorded were part of the Gmail sunset in ADR-033 (Cloudflare email ingress).

## ADR-008: Telegram human-in-the-loop review
*Superseded by ADR-031 · 2026-08-25*

Superseded by ADR-031. Standing rules it set remain: Telegram is finance-only, review replies bind to the stored Telegram message ID rather than inferred model context, webhook intake authenticates `X-Telegram-Bot-Api-Secret-Token` and accepts only private messages from an active numeric Telegram user, and duplicate update IDs create no duplicate jobs.

## ADR-009: Generic finance document intake
*Accepted · 2026-08-25*

All finance images and documents go through one validated attachment pipeline that produces proposals for deterministic validation and reconciliation. Intake accepts JPEG/PNG up to 10 MiB and 24 megapixels from the web API or an authorized private Telegram message; Telegram updates become idempotent `TELEGRAM_IMAGE` source events and share the same attachment, document and `PROCESS_DOCUMENT` path. Captions are supplemental metadata only. Payslips are confirmed as one net-pay income only when high-confidence, arithmetically consistent and dated; allowances and deductions never create expenses. Receipts and screenshots use strict extraction with whole-IDR amounts and Asia/Jakarta times, and evidence attaches to an existing transaction only on exactly one strong match, otherwise it becomes reviewable proposals. Incoming screenshot rows need review, bills and invoices are not payment evidence, and Jago incoming rows stay ignored under `SPENDING_ONLY`. (ADR-042 later allowed per-row screenshot auto-confirm.)

## ADR-010: Transaction proposals before untrusted mutation
*Accepted · 2026-08-25*

Natural language, document extraction and fallback parsing create transaction proposals before any canonical ledger mutation. One source event can hold several independently reviewable proposals (e.g. rows of a history screenshot); `proposal_key` identifies each row without weakening source-event idempotency.

## ADR-011: Attachment storage strategy
*Accepted, extended by ADR-029 · 2026-08-25*

Attachment bytes live outside PostgreSQL, which keeps validated metadata, content hashes and opaque storage references. Stored names are random and household-scoped, never user filenames. JPEG/PNG uploads are decoded, dimension-guarded and re-encoded (stripping metadata) before hashing, and identical bytes share one immutable attachment; every upload source event is retained. Telegram images get the same controls. ADR-029 added the S3-compatible mirror, and with it configured an attachment is accepted only after the mirror succeeds.

## ADR-012: Reconciliation scoring policy
*Accepted · 2026-08-25*

Reconciliation uses deterministic candidate generation and scoring, and only one unambiguous strong match may auto-link; all other uncertainty goes to review. For receipt and screenshot evidence, candidates share household, ledger type, IDR amount and confirmed status and lie within 72 hours. Score starts at 0.45, plus 0.25 / 0.20 / 0.10 for a time distance within 1 / 24 / 72 hours, plus 0.25 for an exact normalized merchant. Auto-link needs one candidate at 0.90 or above, no second candidate above 0.80, a known timestamp, extraction confidence of at least 0.90, and balanced receipt arithmetic where available. Conflicting printed transaction identifiers or unresolved precise-time disagreement block a merge regardless of score (ADR-042 amendment of 2026-10-14).

## ADR-013: IDR-only ledger
*Accepted · 2026-08-25*

The canonical ledger accepts only `IDR`: amounts are `NUMERIC(20,0)` and a database constraint requires `currency = 'IDR'` on every transaction. Multi-currency needs a future forward-only migration and a new decision.

## ADR-014: Monthly category budgets
*Superseded by ADR-051 (2026-10-03) · 2026-08-25*

Budgets were never used. ADR-051 removed the handlers and routes; the `budget` table is kept for history only.

## ADR-015: Tool-first cycle commentary
*Accepted · 2026-08-25*

Analytics commentary is non-authoritative prose that the model builds by calling server-owned, read-only analytical tools; Go computes every number, comparison and authorization, and prose is never parsed back into financial state. The model gets no raw evidence, credentials or database access, and Richmod does not ask it to produce a JSON payload only so Go can parse it. If a tool fails, deterministic analytics stay available and no substitute prose or regex inference replaces it. The implementation is `apps/reviewdomain/analyticscore` (one repeatable-read fact engine, strict schemas, no write capability, no canonical IDs or raw evidence in projections), shared with Telegram. Limits: at most 5 model phases, 5 READs per response and 12 per turn, 30 s per invocation, 120 s overall (125 s worker deadline), generation once per household period per hour, and commentary is unavailable below 0.70 completeness (categorized gross confirmed expense over gross confirmed expense, ×0.90 while reviews remain). Failures retry through the three-attempt queue policy and audit a bounded reason, never provider text. The current prompt contract is `cycle-analyst-v5`, which also exposes the previous closed salary cycle; older rows are kept as historical, not regenerated. The insights API accepts `cycle_start`, omits `facts_snapshot` and `tool_reads`, and responds `private, no-store`.

## ADR-016: Restic for encrypted production backups
*Accepted · 2026-08-25*

A dedicated one-shot backup container with PostgreSQL 17 client tools and restic takes a verified custom-format `pg_dump` and backs it up with attachment storage into one encrypted snapshot. The restic password comes from a root-readable host file and is never committed; ADR-029 derives the repository from the OSS configuration. Retention is 14 daily, 8 weekly and 12 monthly snapshots, scheduled by a host systemd timer. Restore drills may target only a database whose name ends in `_restore_drill`. Production acceptance still needs off-host credentials and a successful restore drill.

## ADR-017: Telegram member self-link invitations
*Accepted · 2026-08-25*

An OWNER creates a household MEMBER, then a 15-minute single-use deep link whose random token is stored only as a SHA-256 hash; invitations are household- and member-scoped, audited, revocable and move through `PENDING`, `CONSUMED`, `REVOKED`, `EXPIRED`. The webhook handles `/start <token>` before normal authorization and, in one transaction, creates the `telegram_identity` from the numeric sender ID, consumes the invitation, audits and queues a confirmation. Usernames and owner-entered numeric IDs are never accepted as proof. Deactivating a member disables membership, identity and pending invitations but keeps history. New members hold an unrecoverable random Argon2id secret until a separate web-password enrollment exists (see ADR-021).

## ADR-018: Explicit merchant category learning
*Accepted · 2026-08-25*

Confirming a reviewed transaction changes only that transaction; a one-off correction must not silently become a rule for marketplaces or supermarkets. A `merchant_alias` is created or enabled (`auto_apply=true`, `created_from_user_confirmation=true`) only on an explicit "remember this merchant" choice: an unchecked box on web, a separately bound yes/no follow-up on Telegram where ambiguous replies create nothing. Aliases are household-scoped and audited, OWNERs can switch `auto_apply` off without deleting history, and ingestion applies only enabled aliases. Alias identity is case-insensitive with collapsed whitespace, unique per household and normalized raw name; duplicates collapse to one disabled rule with removed values recorded in `audit_log`. An `UNKNOWN_MERCHANT` review answered with a name reuses a matching enabled confirmed alias instead of asking for a category again.

## ADR-019: Routed web product and dormant budgeting
*Accepted · 2026-08-26*

The web product is a shared responsive shell with routes Overview, Transactions, Analytics, Review Inbox, Documents, Household and Settings (side navigation on desktop, bottom navigation on mobile), keeping the sliding server session. Logged-out visitors see a public page at `/` and a login form at `/login`, and the browser waits for the session check before choosing which to render. Go and PostgreSQL stay authoritative: filtering and analytics ranges are query-backed and household-scoped, and Recharts only renders API values. Lifecycle changes disable records instead of deleting them. Budget handlers were later removed by ADR-051; the table remains. Pages follow explicit load/busy state helpers in `apps/web/app/lib/useLoadState.js` (`useGuardedLoad`, `useDrawerRecord`, `useBusyMap`): only a first load shows a skeleton, superseded responses never set state, a failed list shows an error with retry rather than an empty result, and only a 401 from `/auth/me` signs the user out. `apps/web/tests/product-alignment.test.mjs` guards these rules.

## ADR-020: Telegram finance assistant queries and inline review actions
*Accepted · 2026-08-26*

One strict gateway extraction classifies supported Telegram intents and emits only bounded parameters (Jakarta date period, search text, explicit correction fields); Go validates them, and household-scoped PostgreSQL queries select records and compute IDR totals that are never sent back to the model for wording. Searches return at most six recent matches, disclosure ranges are capped at one year, and a correction mutates only when its bounded search has exactly one result, with an audit event. Callback data holds only an allowlisted action or category slug, never a transaction ID: the worker resolves the transaction from the stored `review_request` household/chat/message binding and re-authorizes the numeric Telegram identity. `UPLOAD_FINANCIAL_DOCUMENT` points to the generic document pipeline.

## ADR-021: Multi-user dashboard authentication
*Accepted · 2026-08-26*

Household membership is `OWNER` or `MEMBER`. Dashboard enrollment uses a single-use 24-hour invite whose SHA-256 token hash is stored in PostgreSQL and whose token travels in the URL fragment over HTTPS; acceptance sets a password and creates the normal sliding 24-hour HTTP-only session, and members cannot log in before enrolling. A separate `is_super_admin` user flag grants admin-console access only and never bypasses household-scoped financial authorization; it is set through the idempotent bootstrap command. Invite tokens are never persisted or logged in plaintext. ADR-059 extends this for super-admin household provisioning.

## ADR-022: Dedicated Telegram interactive callback lane
*Superseded by ADR-026 · 2026-08-26*

Superseded by ADR-026, which keeps the design: callbacks are immutable `TELEGRAM_CALLBACK` source events processed by `PROCESS_TELEGRAM_CALLBACK` jobs on an `INTERACTIVE` lane, reuse deterministic review transitions and never become LLM text requests.

## ADR-023: Universal review items
*Accepted, amended by ADR-046 · 2026-08-26*

Every human review opportunity is a `review_item` row, belonging to one household and pointing at a transaction, proposal, source event, document or other canonical subject; it is the canonical Review Inbox backlog. `review_request` stays a Telegram delivery/conversation projection linked to the item and, per ADR-046, must not depend on a transaction-only subject. Ambiguity can be persisted before a transaction exists, web and Telegram resolve the same item, and new review types must declare and test Telegram interaction capability rather than ship Web-only.

## ADR-024: Native finance tool-call harness
*Accepted · 2026-08-26*

The gateway may return native `function_call` items for an allow-listed finance tool set. Go parses and validates the tool name and JSON arguments and runs the operation inside household authorization and audit boundaries; the gateway client never executes tools or holds database credentials. Unregistered or malformed calls fail closed.

## ADR-025: Config-driven bank-email ingestion
*Accepted · 2026-08-28*

Bank notification sources are household-scoped listeners; the mail source only establishes trust and persists evidence. The worker uses one required native `emit_bank_transaction` call, validates it in Go and applies the fixed `SPENDING_ONLY` policy, so model output cannot mutate the ledger. A valid transaction without a time uses the trusted source-event receipt time as an `EMAIL_RECEIVED_AT` reference and goes to normal review for merchant/category/detail; the model may add an optional bounded review summary only. Adding a bank sender is a settings operation: no bank-specific parser, sender environment variable, migration seed, prompt or compatibility flag exists in the active path.

## ADR-026: Durable Telegram ingress and isolated job lanes
*Accepted · 2026-08-29*

The webhook authenticates, validates a bounded callback grammar (`review:*`, `pending:action:yes|no`, `pending:batch:yes|no`) and atomically persists source evidence plus a queue job before returning HTTP 204; the API holds no Telegram token and makes no Telegram call. The grammar lives once in `reviewdomain.ValidTelegramCallback`, used by both the webhook and the worker (a worker test fails if the worker emits a callback the grammar rejects), and out-of-grammar callbacks are dropped with 204, so a new button must extend it in the same change. The worker acknowledges callbacks first within 1.5 s; ACK failure is logged and does not block the bound action. Lanes: callback, send and edit are `INTERACTIVE`; ordinary Telegram text is `DEFAULT`; bank, document, image, payslip, screenshot and insight work is `BACKGROUND`. A trigger assigns lanes, each lane has its own consumer, and consumers yield after 25 jobs, so at most two non-interactive LLM jobs run at once and slow LLM work cannot starve button actions. (ADR-032's CHAT lane was later retired.)

## ADR-027: Single-protocol bounded LLM calls and redacted observability
*Accepted, amended by ADR-033 · 2026-08-29*

`LLM_GATEWAY_PROTOCOL` selects exactly one protocol, `responses` (default) or `chat_completions`; a call never retries on a different protocol, and responses are capped at 2 MiB (the chat adapter converts `input_text`/`input_image` parts and rejects unsupported ones locally). Go owns task budgets: bank extraction 45 s total with one corrective call only after a schema-invalid reply, document stages 60 s, insights per ADR-015, and Telegram free text per ADR-033 (130 s turn, 25 s per model call, progress notice after 10 s, at most 5 phases, 4 READs per response, 8 per turn, one side effect). The additive `llm_call` table stores only task, protocol, model, status, duration, usage, cost, attempt, call kind, tool names and household; prompts, responses, emails, documents, messages, tool arguments and financial results never enter telemetry. Strict single-result workflows accept exactly one allowed native call; the Telegram conversational adapter accepts display text, an allow-listed READ batch or one side-effect call, and fails closed on unknown or malformed calls.

## ADR-028: Canonical universal review orchestration
*Accepted, amended by ADR-046 · 2026-08-29*

`review_item` is the canonical household backlog for transactions, proposals, source events, documents, Wealth observations, financial-email observations and other subjects; `review_request` is an optional Telegram projection, so a review exists even when Telegram is unlinked or delivery fails. ADR-046 adds that when an eligible active Telegram recipient exists, every currently producible human review must have an actionable Telegram projection; "optional" does not license Web-only reviews. Active-subject uniqueness is enforced in PostgreSQL and resolution metadata is retained. Incomplete bank extraction may create a source review with no transaction, and a first valid payslip a proposal-backed review. Cross-surface and multi-recipient races are settled by locking and revalidating `review_item`; the first valid resolution wins.

## ADR-029: S3-compatible off-host storage
*Accepted · 2026-08-30*

One private S3-compatible bucket holds off-host data under a configurable `OSS_PREFIX`: `<prefix>/attachments/<household-id>/<opaque-name>` and `<prefix>/backups/restic/...`. Document bytes are written to the local volume and mirrored to S3 before PostgreSQL metadata commits; worker maintenance removes local bytes once the document is terminal and no document job is active, and later reads go straight to S3. Original filenames never become keys. Backups stay `pg_dump` archives inside encrypted restic snapshots whose keys are independent of OSS credentials and need an off-host recovery copy. The bucket stays private and, after session and household authorization, document-content endpoints answer with a two-minute GET-only presigned redirect that is never persisted or logged and carries `Referrer-Policy: no-referrer`. Consequences: temporary OSS failure rejects new uploads and remote reads, and existing local attachments need one idempotent backfill.

## ADR-030: Native-only model tool contract
*Accepted, partially superseded by ADR-033 for the Telegram conversational lane · 2026-09-01*

## ADR-033: Bounded natural conversational finance agent
*Accepted, amended by ADR-038; evidence context extends it in ADR-050; amended 2026-11-05 (agent loop hardening) · 2026-09-12*

Telegram free text is handled by a bounded conversational agent in Go: the model may understand, retrieve, reason, explain and propose, while Go authorizes, validates, reconciles, reviews, audits and commits and PostgreSQL stays canonical. The earlier "exactly one tool call ends the turn" contract turned the model into an intent classifier without improving ledger safety, since the safety boundary is what can change canonical state. A model response is valid in exactly one shape: display-only text (never parsed into an action), a batch of allow-listed READ calls (run concurrently, results fed to the next phase), or exactly one allow-listed side-effect call. Mixed, multiple-side-effect, unknown, unavailable or malformed calls are rejected before anything runs, and tool availability follows server state. Server-owned limits: 5 model phases per turn, 5 READs per response, 8 READs and 1 side effect per turn, 25 s per model call (one retry after a timeout), a 130 s turn (160 s queue budget) and a one-time progress notice after 10 s. Go binds targets in order: exact callback or `reply_to_message_id`, exact pending action/batch, one uniquely eligible active review for that recipient's chat, opaque server-scoped refs from earlier READs, and only then model interpretation of the change itself; an exact reply is never displaced, ambiguity hides the mutation tool, and bindings are revalidated under lock in the mutating transaction and fail closed when stale. `IGNORE` is a dismissal and never records `TRANSFER_RECONCILED`. Analytics refs are valid only in the turn that issued them (stale ones return the recoverable `REFERENCE_NOT_ISSUED`). Memory is the chat's stored turns of the last 24 h (40 rows read, newest 3 user exchanges kept whole, older rows clipped to text, 6,000-character budget), compacted deterministically because a model-written summary would put untrusted numbers into later prompts. Post-mutation wording sees only the model-safe result and a synthesis failure never undoes the mutation; strict single-tool contracts remain for classification and extraction (ADR-030). The 2026-11-05 hardening (from production latency and lost-answer data) made memory count exchanges, stored failure replies as turns, classified errors (recoverable refusals go back to the model, an unreachable gateway defers the message up to 24 h per ADR-052, a 4xx is never retried), answered known mutation results deterministically in the mutation's own transaction, bound typed answers to open cards by Go rules (several matches get a "which card?" prompt via `pending:card:<token>`), merged overlapping read tools, offered no tools on the last phase, limited amount/merchant corrections to household-entered transactions (else `SOURCE_EVIDENCE_FIXES_AMOUNT`), staged unknown-category batch items for review, and serialized each household's text jobs on the `DEFAULT` lane.

## ADR-033: Cloudflare email ingress and two-deploy Gmail sunset
*Accepted; Deploy 2 completed in production 2026-09-05 · 2026-09-04*

Forwarded financial email arrives at a generated, opaque, household-scoped address at `richmod.link`. Cloudflare stores the raw RFC822 in R2 and queues only delivery metadata; a delivery Worker posts the raw bytes to `POST /finance/v1/email/inbond`, authenticated by HMAC-SHA256 over timestamp, recipient, envelope sender and body SHA-256. Go validates MIME, authentication evidence, exact household listener match and idempotency, then creates the `source_event`, `bank_email_event` and a `PROCESS_BANK_EMAIL` job, never calling the LLM or writing ledger state at the transport boundary. `PROVISIONED` addresses record transport verification only; `ACTIVE` ones are the household's sole financial provider. Invariants: the recipient (never sender or model output) selects the household, Gmail and Cloudflare are never both active for a household, duplicate payloads create nothing, raw email evidence is retained and historical Gmail source records survive. Authentication-service policy is configuration (`EMAIL_INGRESS_TRUSTED_AUTHSERV_IDS`); an ACTIVE delivery without it is recorded as ignored and creates no financial state, and no bank or sender is hardcoded. While `PROVISIONED`, a deterministic control-email dispatcher turns setup mail such as Gmail forwarding confirmation into `integration_action` rows shown in a separate Integration Action Inbox, never in `source_event`, the Review Inbox, the ledger or the LLM; verification URLs are owner-only, pass a Google host/path allowlist and are opened only by the user's browser. Deploy 1 kept Gmail for safety; Deploy 2 removed the Gmail integration, jobs, configuration, dependencies and runtime tables, so Cloudflare email ingress is the only financial-email path and Richmod no longer calls Google APIs. Operations live in `docs/runbooks/cloudflare-email-ingress.md`.

## ADR-036: Wealth, Savings, and Cycle Reconciliation
*Accepted, amended 2026-11-15 · 2026-11-05 · 2026-09-06*

Wealth observations and savings intent are additive: `transaction` stays the cashflow ledger, `purpose` classifies confirmed transfers without making them expenses (existing rows backfilled conservatively: transfers `INTERNAL_TRANSFER`, others `GENERAL`, no historical savings inference), wealth snapshots are point-in-time observations, and closed salary-cycle residuals are review metadata, never synthetic transactions. `review_item` gains `cycle_residual_case_id` (exactly-one-subject constraint, idempotent active-residual index). Bank Email stays the frozen `SPENDING_ONLY` pipeline; Financial Provider Email is a separate generic native-LLM observation pipeline where provider mail is valid standalone evidence, bank mail is optional corroboration, one real event is one canonical transaction with many evidence rows, and provider names are fixture data, never production branches. Each provider-email observation is staged, reviewed and bound separately; a successful extraction with zero observations is durable and never re-extracted; provider-reference reuse needs compatible account, amount, time, purpose and Wealth target; preview runs the same planner with zero canonical mutation; more than ten candidates fails closed. Cashflow is `income - (expense - refund)` everywhere, and Analytics and Wealth share one current-period resolver (confirmed primary salary cycle, else Jakarta month; open periods end at the next Jakarta midnight). Wealth screenshots use the `extract_wealth_observation` tool into the non-ledger `wealth_observation` queue with a `WEALTH_OBSERVATION_CONFIRMATION` review: Go may match an exact account, the model never supplies an ID, and an observation only prefills one value of a complete snapshot. Snapshot correction keeps the original account membership and edits items in place with before/after audit. Ambiguous Telegram transfers persist a bounded `transfer_reconciliation_case` (interpreted facts plus candidate transaction IDs): the user merges one candidate or confirms a new transfer, and weak evidence never selects automatically. A transfer or open expense review may become `ASSET_PURCHASE` by choosing one compatible Wealth Account, reclassifying the same transaction and keeping its evidence. Cross-household validation stays in the service layer and residual generation runs after salary commit via an idempotent job. **2026-11-05 amendment:** choosing the account on a wealth-observation review accepts it and resolves the review in one transaction (no auto-created partial snapshot); `TRANSACTION_MISSING` on a residual returns the cycle dates for manual entry and `RefreshOpenCycleResiduals` reopens the review when a transaction lands in the cycle; a transfer case with more than ten candidates offers merges into the ten closest in time (`RankTransferCandidates`/`LoadTransferMergeSet`, gated by `reviewdomain.TransferMergeable`) while a new transfer beside an overflowing set still fails closed; and cross-lane dedup makes receipt, screenshot row and bank email check all CONFIRMED and NEEDS_REVIEW household transactions first, linking a unique strong match as evidence, sending weaker plausible matches to `POSSIBLE_DUPLICATE`, never auto-merging two bank emails, and holding a per-household/amount advisory lock (`LockLedgerEvent`) while re-checking. **2026-11-15 amendment (cycle wealth boundary rule):** the Analytics cycle review picks its two Wealth snapshots by cycle boundaries, not as the last two snapshots: `wealth.current` is the newest snapshot observed inside the cycle (after the start day, before the measured cutoff) and `wealth.previous` is the newest at or before the start day (day granularity, so a snapshot at 00:31 on the start day is the baseline). `netWorthChange` is `current - previous`, with confirmed cashflow taken over `(previous, current]` and the remainder reported as valuation and other change. With no in-cycle snapshot there is no delta (`netWorthChange`, `confirmedCashflow` and `valuationAndOtherChange` are null, blocker `WEALTH_SNAPSHOT_BEFORE_CYCLE`) and `previous` is shown as the latest observation (so on the start day itself a snapshot taken that day is the baseline/latest observation, not an in-cycle one, until a later snapshot lands inside the cycle; the card says there is no new observation since the cycle began rather than none at all); with no snapshot at or before the start day the delta is null with `MISSING_PREVIOUS_WEALTH_SNAPSHOT`. (Amended 2026-11-15, section facts for the analytics detail sections, all Go-computed in the same `cycle-review-v1` payload, no new endpoint.) `categoryHistory` gains `totals[]` (each cycle's net expense, equal to `history[].expense`), `selectedIndex`, and `deltaVsPrevious` on every row, on `other` and as `totalDeltaVsPrevious`, each the selected cycle minus the column before it (null when there is none). While the selected cycle is ACTIVE it also carries `sameDay`, the same matrix with every cycle cut at the selected cycle's elapsed day count (`elapsedDays`; a shorter cycle is measured to its own end, the active cycle to its cutoff) and the same rows, so a running cycle is never set against full ones without the server saying which; it is `null` for a closed cycle. `merchantRanking` ranks the cycle's payees by net amount, largest first and numerically, using the merchant grouping behind `merchantDrivers` (one row per payee; `kind` is `MERCHANT`, `COUNTERPARTY` for a named payee with no merchant, or `NONE` for the no-merchant, no-counterparty row labelled "Tanpa merchant"), at most ten rows with `count`, `previous` and `deltaVsPrevious` per `comparison.mode` (previous eligible cycle at the same elapsed day while ACTIVE, previous full cycle once CLOSED; null with no earlier cycle), plus `other` (`merchantCount`, `count`; payees beyond the top ten and those with a zero or negative net) and `total`; `other` is net expense minus the listed rows, so rows + other = total = `cashflow.expense` to the rupiah, on both the current and previous side. `GET /api/v1/transactions?merchantId=none` lists transactions with no merchant and no counterparty name, so the "Tanpa merchant" row links through; a named but unresolved counterparty is its own payee and is not matched. `memberAttribution[]` gains `kind` (`AUTOMATIC` for the unattributed bucket, otherwise `MEMBER`) and `shareOfExpense`, computed in basis points with largest-remainder rounding so the shares sum to exactly 1.0000 (null when net expense is not positive or any recorder is negative); the server owns the order, automatic bucket first, then members by name, never by amount.

## ADR-038: System One semantic decision plane
*Accepted for implementation, amended by ADR-045, ADR-052 and ADR-053 · 2026-09-20*

Richmod adopts Jev / System One as the bounded semantic decision plane, in this priority: deterministic Go, then Jev for bounded judgment (type, category, transfer purpose, review action, salary choice, merchant-learning consent, evidence support, same-event likelihood), then a generative LLM only for unbounded extraction, vision, reasoning or prose, with Go the final authority. When server state and candidates suffice, the generative call is skipped entirely. Gateway rules: all inference stays behind LiteRouter (`/v1/systemone`), Richmod never calls TypeSafe directly or stores its key, System One is never emulated as a chat model, and a failed Jev decision never falls back to a generative answer to the same question; allowed outcomes are exact deterministic resolution, clarification, Review Inbox, safe retry, or generation only for a genuinely different capability. Jev may only choose among server-owned questions and candidates: no hidden IDs, no bypass of authorization, exact Telegram binding, arithmetic or reconciliation, and no direct database writes. Go may harvest generic candidates (amounts, dates, times, account/merchant aliases, category slugs, opaque transaction refs, allowed actions) but never bank- or provider-specific branches. Generative confidence alone never authorizes a mutation, and Go owns all thresholds, margins and policy versions. `JUDGMENT_MODEL` is a production invariant (the worker refuses to start without it; `JUDGMENT_MODE=disabled-dev` opts out in non-production); when Jev is unreachable deterministic features and READs continue, no mutation tool is exposed and mutations return an explicit non-success while preserving evidence. Every Jev-influenced mutation records bounded `judgment_decision` provenance in the same transaction. Amendments: ADR-045 limits post-generative Jev to residual or independently distinct questions; implicit workflow bindings (an open review, a merchant-learning wait) must never swallow later messages, so lane selection is route-first and only exact bindings (pending correction, batch, salary choice, explicit reply) outrank the route; every route maps to exactly one lane in `judgment_route_lane.go` (`TestEveryServerOwnedRouteMapsToExactlyOneLane`) and a non-terminal route returns control to the conversational agent instead of ending as unclear; inverted claims such as `material_ambiguity` need a decided negative recorded separately (`AmbiguityDecidedNotAmbiguous`), not the undecided band; and a new-merchant category is a bounded choice over the household's active categories instead of an automatic review. ADR-052 later removed Jev from Telegram turns.

## ADR-040: Bank email zero-touch classification
*Accepted for implementation, amended by ADR-045 and several times since · 2026-09-23*

## ADR-042: Per-row screenshot auto-confirm with one bounded ruling per image
*Accepted for implementation, amended by ADR-045 and later · 2026-09-23*

The unit of certainty in a transaction screenshot is the row. ## ADR-045: Single-intelligence-pass routing with residual bounded rescue
*Accepted architecture amendment · 2026-09-24*

Every canonical fact has one primary semantic owner per event (`DETERMINISTIC`, `JEV`, `GENERATIVE_EXTRACTION`, `USER`), chosen by question shape: deterministic exact state, Jev first when the task is already bounded, generative only when extraction, vision or open reasoning is required, then deterministic validation, then Jev only for a residual bounded uncertainty or an independent evidence-support claim, and a human only for irreducible uncertainty or policy intent. This is a decision tree, not a mandatory chain. A model pass that asks the same question about a dimension an earlier pass already settled acceptably (with no residual uncertainty and no independent evidence claim) is a redundant double-pass and is prohibited; combined provenance (`GENERATIVE_PLUS_JEV`) is valid only when Jev resolved a different fact. Generative output is accepted directly only through a source-specific acceptance contract (schema, enum membership, amount range, date provenance, arithmetic, household authorization, exact entity resolution, duplicate and conflict checks, completeness, policy-choice exclusion); confidence is never the sole gate. Call budgets: a simple Telegram transaction uses one Jev bundle and no generative call, a clear receipt one vision pass and no Jev (one residual category rescue if needed), a screenshot one vision pass plus at most one batched Jev request for unresolved rows only, and a failed initial Jev route never silently delegates to generative mutation authority. Missing evidence is never guessed by another model call: a receipt without a date gets `missing_facts=["transaction_at"]`, not `received_at`. A failed residual rescue keeps all valid known facts and opens a minimal review for the residual only. Related batched questions share one Jev call without re-judging resolved rows, ReviewDecision must list only unresolved residuals, telemetry must count calls, rescues and redundant double-passes, and every change to model ordering needs seven regression tests (clear bounded event skips generative, clear extraction skips Jev, one residual calls Jev before a human, missing evidence is not guessed, a Jev failure does not become generative authority, mixed batches take different paths, provenance lists only phases that ran). It amends ADR-038, 040, 041 and 042.

## ADR-046: Universal review interaction projections
*Accepted architecture direction, amended repeatedly through 2026-11-06 · 2026-09-25*

Reviews use three layers: `review_item` plus ReviewDecision as canonical state, one shared review resolution service (lock the item, check it is active, validate household actor, action, supplied residual facts and candidates against current state, mutate, update the decision, audit, return a surface-neutral result), and Web and Telegram as projections that own no mutation policy. `review_request` is a Telegram projection of any `review_item` subject (no `transaction_id` requirement); the canonical item stays resolvable without it, renderers key on interaction mode, missing facts and allowed actions rather than `review_type`, and a coverage test fails if a producible type has no Telegram capability. Callback values must resolve to currently valid household-scoped candidates and models never pick canonical IDs. Callbacks and replies are exact bindings; open review state does not own later messages. Pending correction and batch buttons carry a rotating server-issued `confirmation_token` (migration `00082`) matched with household, Telegram user, chat and unexpired `PENDING` status under the mutation's row lock, so stale buttons change nothing. A review stays open after one residual is supplied and both surfaces re-render it; a duplicate or transfer relationship choice never erases missing category/date facts; source/document state derives from all siblings. A second surface or recipient acting later gets `ALREADY_RESOLVED` and nothing replays; projection expiry never erases the canonical review. No AI authority and no LLM call to render or route bounded callbacks; surface-neutral telemetry without raw values is exposed to Super Admin read-only at `/admin?tab=reviews`. **Amendments:** recipients derive from household ownership (`review_item` household, active member, active `telegram_identity`, `review_request_recipient`), with a source chat only a fallback (2026-09-28); source-only `UNKNOWN_BANK_TEMPLATE` cards dismiss via `IgnoreBankReview` (2026-10-05); typed answers to cards run on the conversational agent with Go validating, and bank-fact cards complete through `COMPLETE_BANK_FACTS` (2026-10-08); incoming `INCOME` rows get income/own-account/household/ignore buttons and `ClassifyTransferReview` accepts `INCOME` only for those (2026-10-13). ## ADR-047: Semantic Fact Ownership and Accepted-Fact Boundaries
*Accepted, amended 2026-09-28 · 2026-09-27*

Every semantic dimension has one current owner (`DETERMINISTIC_KNOWLEDGE`, `GENERATIVE_EXTRACTION`, `JEV`, `USER`) and a downstream layer may consume an accepted fact but never silently become a second owner. A fact is accepted when its owner has met the source or domain acceptance contract, including source-policy-derived facts such as bank-email `EMAIL_RECEIVED_AT` time (kept distinct in provenance but not demoted to missing); known canonical state outranks a redundant missing source hint, and acceptance never waives Go's canonical guards. A consumer may return canonical-safe, an exact validation consequence or residual dimensions, never replace a known value with an inferred one. Handoff is valid only when the previous owner returned unresolved, the user corrects, new independent evidence conflicts, or canonical validation proves a value impossible and repair obtains a new one; repeating a question is not a handoff. Exact household knowledge (aliases, accounts) is deterministic and shared across pipelines when household-scoped, active, unambiguous and allowed by the learning policy, and explicit user statements are `USER` authority. Post-generative Jev is valid only for a still-unresolved material dimension or independent evidence verification. ReviewDecision projects accepted facts as known/proposed, unresolved ones as missing/bounded choices, and must not invent a residual the event lacks. No universal `AcceptedFact` type, table, graph or rules engine is introduced.

## ADR-048: Validation Consequences, Residual Fidelity, and Domain Continuity
*Accepted, amended 2026-09-28 and 2026-10-02 · 2026-09-27*

Validation that affects routing returns a typed consequence from a small vocabulary: `HARD_CANONICAL_INVARIANT` (reject, repair or ask the exact field), `REPRESENTATION_INVALID` (keep other facts, repair or mark the field missing), `INDEPENDENT_EVIDENCE_CONFLICT` (preserve both provenances, bounded verifier or exact conflict review), `BOUNDED_RESIDUAL` (one Jev decision, then one human choice), `QUALITY_SIGNAL` (keep authoritative facts, block only what is unsafe, no review for a generic confidence miss), `HUMAN_POLICY` (ask only the policy choice, e.g. first primary salary) and `CANONICAL_AMBIGUITY` (bounded human selection among plausible candidates). Review residuals derive from consequences with two gates: something is unresolved, and resolving it can change the attempted canonical outcome. A domain candidate survives review and its finalizer owns domain side effects, so an autonomous and a human-resolved finalization produce the same result except for facts the human changed (tests compare side effects, not only status). A payslip stays bound to salary-domain state: a clear payslip with an existing primary salary and known pay date finalizes with no review, first salary source and missing pay date remain policy/evidence reviews, autonomous and reviewed paths call the same salary finalizer in one transaction, and a duplicate period/employer links evidence only when amount and pay date agree. Unknown values must be representable and sentinel values are prohibited. Human review needs an exact human action that changes the outcome: machine, provider or schema failures mean retry, repair or infrastructure state, not review, and an IGNORE-only review is not a garbage-collection lane. ReviewDecision carries optional `validationConsequence` and `affectedFacts`; a receipt line/total mismatch is `QUALITY_SIGNAL` targeting `receipt_arithmetic`. ADR-049 gives terminal machine failures a dismissable Tindakan item instead of a review.

## ADR-049: Failed Sources Surface as Dismissable Actions
*Accepted, amended 2026-11 · 2026-10-02*

A source event that reaches a terminal failure leaves one dismissable `integration_action` of type `SOURCE_PROCESSING`/`SOURCE_FAILED` in the Inbox Tindakan tab (plain copy from `reviewdomain.FailedSourceCopy`), because `/analytics` counted unfinished sources that had nothing behind them in the Inbox, and ADR-048 forbids opening a review for a machine failure. It is recorded in the same transaction that marks the job `FAILED` (`queue.FailWithHook`), immediately for an `INVALID` bank extraction, and for a retryable failure only when the job gives up; the dedupe key is the source event ID. Closing it (owner-only) sets the source event `IGNORED` in the same transaction only while still `RECEIVED`/`PROCESSING`/`FAILED`, audited as `IGNORE_FAILED_SOURCE`. Telegram messages and taps also get one plain reply when the job dies, and analytics links to `/inbox?view=actions`. No schema change; earlier failures have no item, and a source stuck without a failed job stays counted on purpose. The 2026-11 amendment made the queue a state machine with explicit lease ownership: `Succeed`, `Defer` and failure writes are conditional on `locked_by`, a running job renews its lease every minute (`KeepLease`), a reclaim past the last attempt fails the job through the permanent `LeaseExpiredError` path, and every job type that settles a row has a final-failure step in the failing transaction (document follow-ups, `PROCESS_FINANCIAL_EMAIL`, `PROCESS_FINANCIAL_EMAIL_PREVIEW`, `GENERATE_INSIGHT`).

## ADR-050: Conversational Evidence Understanding (CEU)
*Accepted · 2026-10-03*

CEU adds deterministic conversational binding and a model-safe evidence context, and no decision authority. Binding is server-owned and ordered: exact reply, active evidence-backed review, valid opaque ref, the one immediately preceding evidence (newest from this user in this chat within 10 minutes), a bounded recent set, then one clarification question; a model never chooses evidence when a deterministic level can, and an exact reply that resolves to nothing is terminal. Turn-local, cross-turn (opaque, household + Telegram user + chat scoped, expiring, resolved only by Go, at most 60 minutes) and canonical references stay distinct, and canonical IDs are never model-visible. The evidence unit is the `document` (covering albums). The Evidence Context Package separates `observed`, `canonical` and `workflow` data, carries no UUIDs, OCR text, storage refs or confidences, and wraps evidence-derived strings in `<untrusted_evidence_text>`. Corrections reuse `resolve_review`, `propose_transaction_correction` and the existing finalizers; a CEU or provider failure opens no review. Owner decisions: auto-resolved receipts and payslips send a bindable "recorded" notice to the originating chat, ambiguity yields one clarification rather than a Jev choice, and `source_event` gains a nullable indexed `telegram_chat_id` so a reply to an upload binds by household, chat and message ID. `get_evidence_context` is a READ though it writes a bounded idempotent ref row. The 2026-10-14 amendments add the side-effect tool `dispute_evidence_link` (no arguments) for an exact reply saying a merged screenshot is a different transaction: Go validates household, Telegram user, exact binding, one merged row with known amount and date and exactly one active link, and stages a `POSSIBLE_DUPLICATE` review (provenance `evidence_link_dispute`) over a new `NEEDS_REVIEW` row, resolved only by `review:dispute:confirm`/`reject` (confirmation marks the old link `SUPERSEDED` and links the screenshot to the new row; the original proposal and transaction are untouched). Only a single `EXPENSE` row can be disputed; the category comes from the screenshot's own validated extraction (household merchant memory overrides only when it agrees), an unresolved category goes through the category chooser, and a rejected dispute can be raised again. Rejected alternatives: a CEU agent, letting the model pick among evidence, an evidence-memory or vector table, exposing extractor confidence, a new correction tool, and replaying refs from memory.

## ADR-055: Rejected tool arguments get one bounded repair round

## ADR-059: Super Admin household provisioning
*Accepted, extends ADR-058 and ADR-021 · 2026-11-05*

`POST /api/v1/admin/households` (Super Admin only, same-origin, unknown fields rejected; `householdName`, `ownerName`, `ownerEmail`, optional positive `telegramUserId`) and `/bootstrap --new-household` both call `internal/provision.CreateHousehold`: household, a new `OWNER` user, optional Telegram identity and default categories in one serialized transaction audited as `CREATE_HOUSEHOLD`; an existing email returns `409 USER_ALREADY_EXISTS` and no user is ever attached or moved. Identity bindings are 1:1 and permanent (migration `00088`: `household_member(user_id)` and `telegram_identity(user_id)` unique, and `telegram_identity(household_id, user_id)` must reference that user's own membership), so a Telegram ID bound to anyone, including a removed member, returns `409 TELEGRAM_ID_ALREADY_LINKED`, the link-invite flow follows the same rule through `provision.BindTelegramIdentity`, and an owner without a Telegram ID links later via `POST /api/v1/household/members/{id}/telegram-invite`. No password passes through the API: the owner gets an unusable random password and a single-use 24-hour invite (only the SHA-256 is stored) shown once as an `/invite#…` link; `POST /api/v1/admin/households/{id}/owner-invite` replaces the pending invite until the owner enrolls, then returns `409 OWNER_ALREADY_ENROLLED`. Creating a household does not make the Super Admin a member or grant access to its data, and both actions are written to `platform_audit_log` (`ADMIN_CREATE_HOUSEHOLD`, `ADMIN_REISSUE_OWNER_INVITE`). The owner link is a bearer credential held by the Super Admin until enrollment, which is inherent to console provisioning without outbound email. Passwords are reset by the same invite link (no self-service reset): owners issue members a reset link (`purpose: RESET`), the Super Admin posts `{"reset": true}` to the owner-invite endpoint (audited `ADMIN_RESET_OWNER_PASSWORD`), and opening a reset link replaces the password and revokes all that user's sessions while the old password works until then.
